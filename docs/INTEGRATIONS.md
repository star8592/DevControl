# DevControl Integration Architecture

DevControl should remain a project-control core, not become a browser shell with unrestricted local execution.

## Recommended layers

1. **DevControl Core**
   - project registry
   - status aggregation
   - workflow / runner state
   - task and approval state
   - safety policy
   - audit log

2. **Provider adapters**
   - GitHub
   - GitLab / Gitea later
   - local filesystem / git status later
   - issue trackers later

3. **AI adapters**
   - Codex CLI for coding work on the local Linux host
   - OpenAI API for chat, planning, summaries and triage
   - optional local OpenAI-compatible model for low-risk summaries

4. **Local Tool Bridge**
   - `git` read-only status/diff/log
   - `gh` status / PR / Actions views
   - editor launcher (for example VS Code)
   - optional OS-specific GUI launchers

## Why Codex should be the primary coding integration

The project console already has repository state, local paths, workflow failures and safety boundaries. A Codex adapter can receive a compact project context and perform a bounded coding task in the selected repository.

Recommended modes:

- `plan`: no file writes
- `review`: no file writes
- `edit`: project-path writes allowed
- `test`: commands from an allowlisted project test profile
- `push`: separate approval gate

Never pass arbitrary browser-provided shell text directly to a local shell.

## Chat panel

A chat panel is useful, but it should be a **DevControl project assistant**, not an embedded copy of the ChatGPT website.

Useful context automatically attached to a chat turn:

- selected project
- current phase
- latest commit / PR
- latest CI and self-hosted result
- blocker
- next action
- recent safe log excerpts
- project safety policy

Suggested actions generated by chat should remain proposals until an explicit control adapter accepts them.

## Local model

A local model is optional and useful for:

- log summarization
- classification
- status explanations
- low-cost repetitive triage

Do not make a local model the authority for release, trading, frozen-data mutation, production switching, or other high-risk controls.

## GitHub Desktop

Treat GitHub Desktop as an optional GUI launcher on operating systems where it is supported. DevControl itself should rely on Git/GitHub APIs and `gh`, not GitHub Desktop, because the server must remain portable and headless-friendly.

On the current Linux control host, prefer:

- `git`
- `gh`
- Codex CLI
- VS Code / another editor launcher if desired

## Security rules

- localhost binding by default
- browser never receives GitHub/OpenAI tokens
- no arbitrary shell endpoint
- project paths come from the trusted registry, not browser text
- all write actions are deny-by-default
- every write action gets an audit record
- destructive/high-risk actions require an explicit project-specific approval policy
- secrets and unredacted credential-bearing logs are never sent to AI providers

## Planned API shape

```text
GET  /api/projects
GET  /api/status
GET  /api/integrations
POST /api/ai/plan
POST /api/ai/review
POST /api/control
POST /api/local/open-project
GET  /api/audit
```

The AI layer proposes. The control layer decides and executes.
